blip action ideas

How an actions view could tell apart what you asked for, what the target agreed to and what it reports back. Built from the colours and fonts in theme.rs, at the app's size.

1Setpoint and readback on one scale

Today the readback is plain text in its own column, styled like the input next to it, so 1806 rpm in the slider box and 1806 rpm beside it look like the same thing. The proposal draws the readback as a blue needle on the slider track, the way a controller faceplate shows setpoint and process value: the handle is what you asked for, the needle is what the target reports, and the shaded gap is the distance still to go. Blue already means live data in blip.

Actions 1

A simulated motor follows its setpoint in about a second. Try: untick enable and drag speed (the target rejects it), run calibrate, and switch the link to Answers lost or Down, then compare Now with Proposed.

2An input never shows a value the target refused

When the target rejects a slider value today, the slider stays where you left it and a warning icon appears in the far column, with the reason only on hover. The view then claims a setpoint of 2500 rpm that does not exist. Inputs that send at once should spring back to the last accepted value and say in a line what was refused and why. Forms with a Send button are different: their inputs are a draft, so they keep what you typed and show the reason below.

3Confirm in the row, select before operate

The dialog asks Carry out imu/calibrate? with the raw path, no description and, for actions with parameters, none of the values it is about to send. The row button says Run or Send, the dialog says Run either way. Substation and plant HMIs solve this with select before operate: the first click selects the action in place and the second, on a different spot, carries it out; the selection lapses after a few seconds. Kept in the row, the live readback and the plots stay in view while you decide, and the values being sent are right there.

Either way the row button gets an ellipsis, Run… or Send…, the usual sign that a question follows, and the confirming button repeats the verb with the action's name. Enter should not confirm.

4Show what has not been sent yet

A form with a Send button, a text field that sends on Enter, an integer field that sends on leaving it: in all three, a typed value that was never sent looks exactly like one that was. A small dot by each changed input, cleared when it is sent, makes the draft visible. The text field also hints at Enter while it holds unsent text.

5Outcomes next to the input, in words when they matter

The outcome icon sits in a fourth column past the readback, far from the input it belongs to, and a refusal or a missing answer is only a coloured glyph. Proposed: the icon follows the readback directly, and anything you need to act on gets a line below the row that stays until the next invocation.

6Smaller fixes found on the way

  • Late answers are dropped. After five seconds an invocation counts as unanswered and a later answer is ignored, but the outpost only answers once the action returns. An action that takes six seconds and succeeds shows the clock for good. Keep counting and let a late answer settle it.
  • Flicker while dragging. Each of the ten sends a second shows a spinner, then a check for 1.5 s, so the outcome column blinks during a drag. Show one steady state while dragging and the outcome of the final value on release.
  • Readbacks that stopped. With the connection down the inputs grey out, but the readback keeps its last value at full strength. Dim it and give its age, as in the demo with the link Down.
  • Bool and choice readbacks repeat the input. A ticked checkbox next to the text true says the same thing twice. Show the text only while it differs from the control, e.g. reads off right after you tick it.
  • Text fields send on Enter only, integer fields also on leaving. Pick one rule for both, or show the hint from idea 4.

7Actions with several values as one thing

The rows of an action with several parameters are 8 points apart, as are the actions themselves, so nothing holds them together. The parameter names sit in the column of the action names, only indented and greyer: the level of message reads like the action level above it. The name of the action stands alone on an empty row, and Send on another.

The proposal keeps one value per line, so sliders, units and the dots of unsent values keep their room, and moves the parameter names out of the column of action names. The action name sits on the row of its first value, and the rule runs down to Send, so the group reads as one action from its name to its button. With the spacing of the second sketch it costs no extra height. One line per action is the most compact, but it wraps beyond three short values and hides the names in the fields.
